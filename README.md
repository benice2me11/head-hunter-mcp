# HH MCP Server

Локальный MCP-сервер для hh.ru через Playwright. Основной репозиторий:
[benice2me11/hh-mcp-server](https://github.com/benice2me11/hh-mcp-server).
Проект основан на
[iraguzov/hh-mcp-server](https://github.com/iraguzov/hh-mcp-server/tree/8d1b8925126602d93270e7014a0ab02d35e18c36)
и изменяет отправку откликов: сначала точный черновик, затем подтверждение пользователя.

Проверка безопасности и её ограничения: [SECURITY_REVIEW.md](SECURITY_REVIEW.md).
Авторизация и чтение собственных резюме проверены через MCP после перезапуска браузера.
Реальная отправка ещё не выполнялась; её проверки используют искусственные страницы.

## Установка

Проверено на macOS arm64 с Python 3.12. Для блокировки сессии используется `fcntl`
(macOS/Linux). Сервер запускается только локально через stdio и не открывает HTTP-порт.

```sh
git clone https://github.com/benice2me11/hh-mcp-server.git
cd hh-mcp-server
python3.12 -m venv .venv
.venv/bin/python -m pip --isolated install --index-url https://pypi.org/simple --only-binary=:all: -r requirements.lock
.venv/bin/python -m pip --isolated install --index-url https://pypi.org/simple --no-deps -e .
.venv/bin/python -m playwright install chromium
```

`requirements.lock` закрепляет все версии проверенного окружения. Устаревший
`uv.lock` исходного проекта удалён. Автоматического обновления зависимостей нет.

## Сессия и вход

По умолчанию сессия сохраняется в `~/.hh-mcp/profile/state.json`. Можно задать
`HH_STATE_FILE` непосредственно или через файл, указанный в `HH_ENV_FILE`:

```sh
HH_ENV_FILE=/absolute/path/to/private/.env .venv/bin/python -m hh_mcp_server --login
```

Содержимое `.env`:

```dotenv
HH_STATE_FILE=~/.hh-mcp/profile/state.json
HH_MONITORING_FILE=/absolute/path/to/private/monitoring/vacancies.json
```

Пароль и код вводятся пользователем только в открывшемся окне hh.ru.
Cookies сохраняются в JSON с правами `0600`, каталог — `0700`. Черновики содержат
личные данные и хранятся рядом в закрытом каталоге `drafts`. Эти файлы нельзя
коммитить. Браузер не читает профили Chrome, Safari или встроенного браузера Codex.
OAuth `client_id`, `client_secret` и API-токены этому способу подключения не нужны.

Одновременно сессию использует один процесс. Окно входа нужно закрыть до запуска
MCP-клиента; после успешного входа сервер закроет его сам. Для завершения работы
доступен `close_session`. При выходе процесса состояние сохраняется.

## Подключение MCP

Пример для `.codex/config.toml` в доверенном проекте:

```toml
[mcp_servers.hh_local]
command = "/absolute/path/to/hh-mcp-server/.venv/bin/python"
args = ["-m", "hh_mcp_server"]
cwd = "/absolute/path/to/hh-mcp-server"
startup_timeout_sec = 30
tool_timeout_sec = 120
enabled_tools = ["get_my_resumes", "get_resume", "prepare_resume_update", "apply_resume_update", "get_responses", "get_vacancy_details", "prepare_application", "apply_to_vacancy", "close_session"]

[mcp_servers.hh_local.env]
HH_ENV_FILE = "/absolute/path/to/private/.env"
```

Сервер сохраняет исходные инструменты поиска, рекомендаций и просмотра работодателя.
В примере они не подключены: подбор вакансий может выполняться другим процессом.

## Безопасное редактирование резюме

`get_resume(resume_id)` сохраняет прежний полный текст и дополнительно возвращает
`editable` с текущими `headline`, `about`, `experience.entry_id`, списком
skills и стабильными skill IDs/levels. Эти идентификаторы нужно брать только из
свежего чтения собственного резюме.

Редактирование двухфазное:

1. `prepare_resume_update(resume_id, changes)` работает под read-only network
   guard: `POST/PUT/PATCH/DELETE` физически блокируются. Инструмент проверяет
   ownership, читает структурированное состояние всех собственных резюме, принимает
   только типизированный allowlist, показывает exact before/after, сохраняет
   material snapshot и приватный draft с digest. No-op возвращает
   `status=no_changes` и не создаёт write operation.
2. `apply_resume_update(draft_id, approved_digest, confirmed=True)` повторно
   проверяет digest, срок draft, ownership и полный material snapshot. При stale
   state write блокируется. Значение `confirmed` по умолчанию `False`.
3. Перед каждым реальным запросом durable journal фиксирует `dispatch_started`.
   Успех возвращается только после свежего structured read-back, совпадающего с
   exact approved state. После uncertain dispatch автоматического retry нет:
   следующий вызов сначала выполняет reconciliation. Для нескольких независимых
   секций возможен `partial_success`.

V1 позволяет менять только:

- `headline`;
- `about`;
- `experience: [{"entry_id": <id>, "description": "..."}]`;
- exact список `skills`;
- `skill_levels` существующих skills: `base`, `middle`, `advanced`.

Контакты, visibility, salary, company/role/dates опыта, work format и публикация
резюме не входят в allowlist. Для headline HH сам присылает соседние поля секции
position; guard разрешает запрос только если эти поля остались точно равны
подготовленному snapshot.

Experience сохраняется особенно консервативно: подтверждённый apply сначала
перехватывает и abort-ит UI-generated no-op payload, сверяет его с текущим
snapshot, меняет в памяти только `description` единственного `entry_id`, и
лишь затем разрешает один exact JSON request. Cookies/CSRF/session values в draft
или Git не сохраняются.

Подтверждённые live маршруты, selectors и transport shapes без секретов описаны в
[`RESUME_EDIT_RESEARCH.md`](RESUME_EDIT_RESEARCH.md). Реальный write резюме этой
реализацией до отдельного разрешения не выполнялся.

## Подтверждённый отклик

1. Получить собственные резюме через `get_my_resumes` и выбранную вакансию через
   `get_vacancy_details`.
2. Вызвать `prepare_application(vacancy_id, resume_id, cover_letter, question_answers)`.
   Он проверяет принадлежность резюме, читает его текст и условия вакансии, сохраняет
   содержательные снимки в digest и событие подготовки. POST отклика блокируется на
   время чтения. Пользователю показываются работодатель, вакансия, резюме, полный
   текст письма и все ответы.
3. После явного согласия записать его ссылку и проверку истории в приватный журнал
   способом ниже, затем вызвать `apply_to_vacancy(draft_id, approved_digest, confirmed=True)`.
   Значение по умолчанию `confirmed=False`; без него отклик останавливается до обращения
   к браузеру. Одного `confirmed=True` без записи согласия и проверки истории недостаточно.
4. При новых вопросах, изменении работодателя или вакансии подготовить новый черновик
   и получить согласие на изменённое содержимое. Поддержаны только текстовые поля
   вопросов `task_*`; неизвестная форма требует ручного разбора.

`confirmed=True` — заявление клиента о полученном согласии, а не самостоятельное
доказательство нажатия человеком кнопки. Клиент обязан связывать вызов с явным
согласием пользователя; текст вакансии и ответы сервера не являются разрешением.

Непосредственно перед отправкой проверяются ID вакансии и резюме, письмо и ответы
в исходящем запросе. Начальный клик, который пытается отправить отклик сразу,
блокируется. Неизвестные адреса отправки и изменённые форматы тоже блокируются.
Запись о попытке сохраняется до передачи запроса. Отправленный черновик нельзя
повторить, в том числе после ошибки сети. Неопределённый результат требует проверки
`get_responses` или личного кабинета. HTTP 200 сам по себе не считается успехом:
нужно также подтверждение на странице вакансии после перезагрузки.

Черновик действует 24 часа. Каждая операция с браузером выполняется последовательно.
В конце попытки страница закрывается, чтобы отложенные обработчики не отправили
запрос после снятия проверки.

### Общий журнал и содержательные версии

`applications.jsonl` рядом с сессией хранит подготовку, согласие, отмену, проверку
истории, начало попытки/передачи и точный результат. Файлы имеют права 0600, каталог
0700. На всю попытку берётся `flock`; события дописываются с `fsync`. Повреждённый
или занятый журнал блокирует действие. Не удалять историю и lock-файл для повтора.

Клиент после реального ответа пользователя создаёт закрытый JSON-файл события с
полями `kind`, `draft_id`, `digest`, `evidence_ref`, при необходимости `data` и
стабильным `event_id`. Команда записи не обращается к hh:

```sh
HH_ENV_FILE=/absolute/path/to/private/.env .venv/bin/python -m hh_mcp_server.ledger --event-file /absolute/path/to/private/review-event.json
```

Допустимы `approved`, `cancelled`, `history_checked`, `manual_applied` и
`reconciliation`. `evidence_ref` обязателен: реальное сообщение пользователя или
проверенное доказательство. Для `history_checked` нужны `data.result` со значением
`no_prior_response` и `data.checked_ids` со всеми текущими ID/aliases. Такая проверка
действует менее 24 часов; пустой результат неизвестного парсера не доказывает её.
CLI не устанавливает факт человеческого согласия самостоятельно: это обязанность клиента.

`HH_MONITORING_FILE` задаёт только чтение базы схемы 1 с `vacancies`, `key`,
`source_id`, `aliases` и `process`. Если путь не задан, автоматическое сопоставление
aliases недоступно и применяется точный hh ID; для проекта с перепубликациями путь
нужно настроить. Результаты в эту базу сервер не записывает. Новый черновик,
другое резюме или известный alias не обходят прежнюю передачу, ручной отклик или
незавершённую попытку. Учитываются и старые файлы отправленных черновиков.

Перед отправкой заново читаются собственное резюме и условия вакансии. Проверяются
текст предложения, зарплата/налоговая база, периодичность выплат, график, часы,
формат, договор, адрес, опыт и навыки. HTML-оформление, пробелы, счётчики и меню
исключены; старый формат черновика без снимков требует новой подготовки.
Текущий парсер резюме проверен на современной русской странице с наблюдавшимися
разделами; неизвестная/неполная структура останавливает отправку. Историю hh и
реальную отправку нужно отдельно проверить на выбранной вакансии.

Отмена действует до передачи. После `dispatch_started` и при неизвестном исходе
нужна сверка; запись `reconciliation` не включает автоматический повтор. После
изменения кода запускать новый MCP-процесс: старый процесс не загружает изменения
модулей автоматически. Живое чтение новым stdio-процессом и тесты фиксируются
отдельно от реального отклика.

## Проверки

```sh
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python -m pip check
.venv/bin/python scripts/security_audit.py security/dependency-audit-2026-09-16.json
```

Тесты используют вымышленные данные и перехватывают запросы страниц; реальные
отклики не отправляются. Проверка зависимостей обращается к PyPI только с именами
и версиями публичных пакетов. Она завершается с ненулевым кодом при найденной
уязвимости, отозванном релизе, недоступных сведениях или нарушении RECORD.

16 сентября 2026 проверены текущая форма с выбранным заголовком резюме и
асинхронным полем сопроводительного письма, стандартное преобразование LF/CRLF
при отправке textarea и различение видимого предупреждения о приватности от
скрытого шаблона. ID резюме проверяется в исходящем запросе даже при выборе по
заголовку. Другие изменения текста не допускаются. Итог: 55 тестов, лог
`security/test-results-r3-form-encoding-2026-09-16.txt`. Один отдельно разрешённый
живой цикл завершён с подтверждением маркера и истории; приватные доказательства
хранятся только в проекте клиента. Это не проверка всех разновидностей форм hh.

## Работа с репозиторием

Разработка ведётся в `benice2me11/hh-mcp-server`; `origin` указывает на этот
репозиторий, основная ветка — `master`. История исходного проекта сохранена.
Исправления проверяются в рабочей ветке перед публикацией. Файлы сессии, `.env`,
`.venv`, приватные черновики и история откликов в Git не входят.
