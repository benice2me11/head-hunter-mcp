# HH Resume Editing Research

Date: 2026-09-25

This note records only redacted, reusable facts observed from the current hh.ru applicant UI. It intentionally contains no cookies, CSRF values, resume IDs, request bodies, or personal resume content.

## Official API

The current public OpenAPI specification served by the HH Redoc UI at `/openapi/specification/public` exposes `GET /resumes/{resume_id}` but no applicant endpoint for creating, editing, deleting, publishing, or changing visibility of the authenticated user's resume.

`GET /resumes/{resume_id}` is declared with the public API's OAuth2
`OauthToken` security scheme. The local MCP authenticates with the hh.ru web
session instead, so its existing session is not an OAuth applicant-edit
credential. V1 editing therefore uses the applicant web UI rather than the
public API.

## Observed edit routes and selectors

| Field | Edit route | Value selector | Save selector |
| --- | --- | --- | --- |
| Headline/title | `/resume/edit/<resume_id>/position` | `[data-qa='resume-edit-title-suggest']` | `[data-qa='resume-partial-edit-save']` |
| About | `/resume/edit/<resume_id>/about` | `[data-qa='resume-editor-about']` | `[data-qa='resume-partial-edit-save']` |
| Experience entry | `/profile/edit/experience/<entry_id>?resumeFrom=<resume_id>` | `[data-qa='resume-editor-experience-description-input']` | `[data-qa='profile-layout-save-button']` |
| Key skills | `/resume/edit/<resume_id>/keySkills` | `[data-qa='resume-editor-skills-input']` | `[data-qa='resume-partial-edit-save']` |
| Skill levels | `/resume/edit/<resume_id>/skillsLevels` | repeated `[data-qa='skill']`, `skillName`, `skill-level-1..3` | `[data-qa='resume-partial-edit-save']` |

The resume view exposes experience edit controls as `button[data-qa^='edit-experience-button-']`. The button itself does not expose the persistent experience ID; opening it by GET navigation reveals the ID in the observed edit route. Therefore editable snapshots must resolve and store the entry ID, not rely on a display index alone.

Observed experience edit selectors also include company, position, company URL, start year, end year, and description. V1 changes only description.

## Observed save transport

Headline/title, About and key skills serialize to:

- method: `POST`
- path: `/applicant/resume/edit`
- query: exact `resume=<resume_id>` plus optional single `hhtmSource`
- content type: `application/json`

Observed headline transport uses primitive arrays: `title` is `list[str]`,
`professionalRole` is `list[int]`, and work/travel/employment values are
`list[str]`. Salary remains a structured list. The approved headline appears
at `title[0]`. A volatile string `fingerprintIteration2` is also generated by
the current client.

Observed About payload contains `skills: list[str]` plus the same volatile
fingerprint. The About text appears at `skills[0]`.

Observed key-skills payload contains `keySkills: list[str]` plus the volatile
fingerprint.

This means a partial resume update must not simply allow any request to the
endpoint: the outgoing payload is checked against the exact approved semantic
payload, with only explicitly allowlisted volatile fingerprint metadata
ignored.

Experience Save was observed under a route guard that aborted the request
before the network:

- method: `POST`
- path: `/profile/shards/profile/update`
- content type: `application/json`
- top-level keys: `profile`, `resumeFromHash`
- `profile.experience` contains the full current experience list

Observed experience rows contain `id`, `position`, `professionId`,
`professionName`, `description`, dates, company identifiers and metadata,
`verification`, and resume associations. Fields present in the structured GET
but absent from the observed write transport, such as `companyAreaTitle`,
`companyLogos` and `interval`, are not added to the write.

The current experience textarea did not reliably update React state through a
plain Playwright `fill()`. V1 therefore uses a safer sequence during confirmed
apply: click Save with unchanged UI state under a capture guard, abort and
validate the resulting no-op payload, patch exactly one matching
`entry_id.description` in memory, then arm the exact-write guard and dispatch
that single JSON payload. The baseline request never reaches HH.

Skill levels were also observed without allowing a write:

- method: `PUT`
- path: `/shards/applicant/key_skills/levels/update`
- payload: `userSkillLevels` entries with `category`, `skill_id`, `level_id`
- UI level 1 maps to `level_id=8`, level 2 to `9`, level 3 to `10`

## CSRF/session handling

No CSRF or session secret is copied into source code or drafts. Browser session
cookies remain inside the existing Playwright context. Observed write requests
carried the session cookie plus `Origin`, `Referer` and `X-Requested-With`; no
separate `X-CSRF-Token` or `X-XSRF-Token` header was observed. Guards inspect
request destination and material payload without persisting secret headers or
cookie values.

## V1 boundary

Supported target changes:

1. headline/title;
2. description of an existing experience entry identified by persistent `entry_id`;
3. About;
4. exact key-skill list;
5. skill levels `base` / `middle` / `advanced` for an existing selected skill.

No V1 write changes contacts, visibility, salary, work format, professional
role, dates, company, position, or resume publication/renewal state. Headline
Save does carry neighboring position fields in the HH payload, but the guard
requires them to remain exactly equal to the reviewed current snapshot.
